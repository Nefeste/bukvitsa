# Спецификации

Описания возможностей — то, что пишется **до** кода и остаётся после как ответ на вопрос
«а как это задумано». Спецификация — договор: чего в ней нет, обсуждается до начала
работы, а не выясняется в процессе. Перед спецификацией — проверка по обещаниям студии
([`02-values.md`](https://github.com/Nefeste/gornitsa/blob/main/docs/02-values.md#как-проверить-новую-возможность)
устава): семь вопросов, и ответ на каждый должен быть «нет».

Файл называется `ГОД-МЕСЯЦ-краткое-название.md` — по дате начала работы. Написанная
спецификация не переписывается «чтобы совпало с кодом»: если по ходу дела решение
изменилось, правка вносится в раздел «Что изменилось по ходу работы» в конце файла.

Факты не копируются: числа геймдизайна — в [`../08-game-design.md`](../08-game-design.md),
правила контента — в [`../09-content.md`](../09-content.md), форматы — в
[`../04-data-model.md`](../04-data-model.md), деньги — в [`../10-money.md`](../10-money.md);
спецификация на них ссылается.

## Образец

```markdown
# Название

**Версия:** 0.1.0 **Состояние:** задумано | делается | сделано

## Зачем            — какую проблему игрока решаем, одним абзацем
## Проверка по обещаниям — семь вопросов устава: «нет» по каждому, или почему вопрос не стоит
## Что увидит игрок — экраны и поведение словами, без кода
## Данные           — файлы и ключи хранилища, только новые
## Неудачные случаи — что происходит, когда что-то пошло не так
## Критерии приёмки — список проверяемых утверждений
## Чего здесь нет   — явно отложенное, чтобы не обсуждать дважды
## Что изменилось по ходу работы
```
