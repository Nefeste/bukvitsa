# Как проверяется

Что должно быть зелёным перед каждым push и что прогоняет CI на PR. Кода ещё нет —
описан принятый набор проверок; тесты появляются вместе с кодом по спецификациям, и этот
документ правится в том же коммите.

## 1. Типы и линтер

`npx tsc --noEmit`, `npx tsc --noEmit -p tools`, `npm run lint` — ноль предупреждений.
Правила линтера — копия из «Узоров» (`eslint.config.js`): запрет `Alert` из React Native,
запрет строк для игрока вне `src/i18n/` (тест ниже ловит то, что линтер не видит),
React Compiler.

## 2. Движок

`bun test tools/test` — чистые функции на образцах, без React:

- **Проверка ответа** для всех пяти видов: верно, неверно, регистр, ё/е, дефис, пробелы.
- **Подсказки**: три по порядку; после третьей задача — `peeked`; подсказка не меняет
  ряд у других игроков (ряд — из задачи, не из состояния).
- **Правила рекламы** (`adAllowed`): все границы из [`08-game-design.md`](08-game-design.md),
  «Реклама», по одному тесту на границу: не раньше десятой задачи, не в первый день,
  каждая третья, не чаще раза в три минуты, никогда после задачи дня, никогда при
  «Буквице+». Изменение числа в геймдизайне без правки теста — красный тест.
- **Права** (`canOpen`): первая тетрадь всегда; «Буквица+»; десятки; задача дня и архив
  всегда.
- **Календарь**: `daily(calendar, date)` для первого, последнего и отсутствующего дня;
  `archive` не выдаёт будущее; чередование видов по неделе.
- **События → прогресс**: «12 из 40», подсмотренная, решённая заново, пустой список.
- **Снимок и миграции**: каждый образец из `tools/test/fixtures/saves/` читается
  текущим кодом; `schema` нельзя поднять без нового образца.

## 3. Контент

`bun tools/content/build.ts --check` — все проверки записей из [`09-content.md`](09-content.md),
§5, на реальном `content/`; `bun tools/content/play.ts` — «виртуальный игрок»:
двусмысленные ряды, варианты одной длины, переставляемые части. Отдельные тесты:

- сборка детерминирована: два прогона — одинаковый `pack.ts` байт в байт;
- `content/released.json`: выпущенная запись не меняет текст и ответ без новой `version`;
  выпущенная дата календаря не меняется (золотой тест `tools/test/fixtures/calendar-released.json`);
- стоп-лист: ни одно слово из `content/stoplist.txt` в выпускной сборке.

## 4. Тексты и файлы

- Строки для игрока только в `src/i18n/` и `content/` — тест ищет кириллицу в JSX
  вне этих папок.
- Номер версии совпадает в `app.json`, `package.json`, `package-lock.json` и «Об игре».
- `store/listing.ru.md` — длины полей по правилам RuStore; `store/site/page.ru.md` —
  формат устава (копия `site.test.ts` из соседей с проверкой `facts`).
- `.github/scripts/automerge.ts` — `tools/test/automerge.test.ts`, копия из «Узоров»,
  переносится вместе с `tools/` в 0.1.

## 5. Сквозной сценарий

`npm run export:web && npm run e2e` — Playwright на веб-сборке (копия подхода «Узоров»):
первый запуск → задача дня → решение с подсказкой → «Откуда это» → «Поделиться»
(текст в буфере проверяется) → тетрадь → закрытая тетрадь показывает два пути → настройки
«ещё крупнее» → тёмная тема. Снимки экранов сценария — в артефакты CI, только когда
репозиторий закрыт. Та же проверка на сборке для сайта (`/bukvitsa/test`).

Реклама и покупка в сценарии — через заглушки адаптеров: сценарий проверяет, что ролик
**не** вызывается там, где нельзя (счётчик вызовов заглушки равен нулю после задачи дня
и внутри задачи), и что после «Буквицы+» он не вызывается вовсе.

## 6. Телефон

Перед выпуском владелец проверяет APK на телефоне по короткому списку в описании
выпуска: установка, задача дня без сети, ролик между задачами (тестовые блоки сети),
покупка в тестовом режиме RuStore Pay и «Восстановить покупки», крупный шрифт, тёмная
тема, «Сообщить об ошибке».

## 7. Сборка APK

Только на тег (`android.yml`): проверка подписи постоянным ключом, размер APK, список
разрешений в сборке сравнивается с белым списком проекта (`tools/test/permissions.json`:
`INTERNET`, `AD_ID`, `ACCESS_NETWORK_STATE`, вибрация — и больше ничего); лишнее
разрешение — красная сборка.
